# オフラインOCR 半年戦略 (2026-06 策定)

プロのセールス担当とシニアエンジニアの2エージェントによる提案を統合したロードマップです。

---

## TL;DR

- **次の半年は「OCR精度の追求」ではなく「OCR結果を活用させる導線」に投資する。** v0.6.2 で日本語縦書き・崩し字を完全オフラインで読む土台は完成。今後は「結果を編集・保存・連携できる」体験で離脱を止める。
- **基盤は「永続化レイヤー + ジョブキュー」の2つだけ。** これを最初の6〜8週で作れば、履歴・PDF・バッチ・AI後処理が全部その上に乗る。
- **集客の最大レバレッジは Show HN / Product Hunt の英語圏ローンチ。** 「100% client-side Japanese OCR」は英語圏で技術的に珍しく、HN の話題性とProduct Huntの瞬発力に乗りやすい。
- **広告・有償インフルエンサー・他ブラウザ展開は当面やらない。** CWS レビュー数を 50 超に積むことを優先する。

## 2. 機能ロードマップ（半年）

| 優先 | バージョン | 機能 | 価値 | 複雑度 | リスク |
|---|---|---|---|---|---|
| **P0** | v0.7 | **OCR履歴パネル + IndexedDB永続化** | 高 (「コピー忘れたら消える」不満解消) | M | 低 |
| **P0** | v0.7 | **結果編集ポップアップ** (その場修正→クリーニングルール候補化) | 高 | M | 中（UX設計） |
| **P1** | v0.8 | **PDF直接OCR** (pdf.js経由) | 高 | L | 中（メモリ・進捗UI） |
| **P1** | v0.8 | **バッチ処理基盤** (複数画像/PDFページのキューイング) | 中 (PDF・表出力を解放) | L | 中 |
| **P2** | v0.9 | **Gemini Nano 連携** (整形・要約のみ。翻訳は出さない) | 中 | S (UI既存) | 中（Chrome側API安定性） |
| **P2** | v0.9 | **Markdown表出力 + 表構造手動補正UI** | 中 | S | 低 |
| **P3** | v1.0 | **英語OCR** (PARSeq 英字モデル追加) | 中 | L | 高（モデルサイズ・配布物肥大） |

### 基盤機能（最優先2つ）

1. **永続化レイヤー** — IndexedDB上の `OcrResult` ストア。スキーマは `{id, sourceImage(Blob), regions[], text, createdAt, tags}` を最小で。**履歴・編集・バッチ・PDF・AI後処理が全部この上に乗る。**
2. **ジョブキュー / 進捗バス** — offscreen 側に汎用 Worker プール、service worker 経由で content/viewer に進捗 postMessage。PDF・バッチ・将来のBG-OCRが共有。

> この2つを6〜8週で作れば、P1以降の実装コストが半減する。

### 並行で進める技術的負債

- `src/shared/messages.ts` を discriminated union で型を締める
- offscreen ライフサイクル管理（idle timer + 明示 close、メモリリーク監視）
- `ModelRegistry` 抽象化（将来のモデル追加に備え、宣言的に `{name, url, sha256, inputShape}`）
- Playwright で E2E 1本だけ追加（選択→OCR→クリップボード）
- CI で `dist/` バンドルサイズを PR コメント

### 作らない機能（半年スコープでは）

| 機能 | 理由 |
|---|---|
| 翻訳統合 | 「オフライン」価値命題と矛盾。Gemini Nano でも UI 上は「整形」に留める |
| TTS 音声読み上げ | Web Speech API で誰でも書ける薄機能。差別化ゼロ、サポート負荷だけ増 |
| 複数領域同時選択 | 履歴パネルがあれば連続選択で代替できる。実装後に不要と判明する可能性大 |
| 中国語・韓国語OCR | モデル配布サイズ・品質保証コストが個人開発の体力を超える。英語で先に技術検証 |

### 最もレバレッジが効く3案

1. **A (Show HN / Product Hunt)** — 「100% client-side, zero network, Japanese vertical text」は英語圏で珍しい。ONNX Runtime WebでNDLOCRを動かす話自体がHN好み
2. **C (漫画／日本語学習)** — Yomitanコミュニティは熱量・規模・伝播力すべて揃う唯一のニッチ。「縦書き漫画コマOCR」のデモは英語圏で刺さる
3. **D (SEOコンテンツ)** — ストックとして効く。低コストで継続流入の床を作れる

### 刺さる PR 角度

- 🏛️ **「国会図書館のOCRをブラウザに移植した個人開発者」** — 公共資産の民主化ストーリー、Zennトップ・はてブ・ITmedia向け
- 🔒 **「Send-zero AI: 通信ゼロで動く日本語OCR」** — プライバシーAI文脈、英語圏ブログ・ニュースレター (Ben's Bites系)
- 🛠️ **「ONNX Runtime Web で NDLOCR を動かすまで」** — 技術ディープダイブ、HN/Zenn技術層、実装記事は信頼の通貨
- 🎨 **「崩し字を読む AI を Chrome で」** — ビジュアル + 文化的興味、TV/Web メディア向け

### やってはいけない／優先度低い施策

- **有料広告 (Google/Meta Ads)** — 無料拡張のLTVに対しCAC回収不能
- **インフルエンサー有償案件** — 個人開発スケールでROI不明、ブランド毀損リスク
- **多機能化による差別化** — 「オフライン×日本語」の軸がブレる。PDF・翻訳は要望ベースで後追い
- **X単発バズ狙い** — 一過性。Chrome拡張は検索/コミュニティ経由のCVRが高い
- **Edge/Firefox 展開** — 工数のわりにユーザー母数が小さい。CWSレビュー数50超を先に積む

0. TL;DR

要点
  • 透視変換の 数学ロジックは既に実装済み (src/ocr/engine/perspective.ts、ndlocr-lite-wasm から移植された computeHomography / applyPerspective が動く状態)。
  • 未実装なのは UI (4点ドラッグ) と ビューアーへの組み込み のみ。
  • 既存の「範囲選択 (矩形)」フローを壊さず、 「台形選択」を並列モードとして追加する方針。
  • この HTML は設計方針の共有 + 下部にインタラクティブなドラッグ プレビュー (実際の Canvas + 実際の computeHomography 相当のロジック) を含みます。実装イメージを触って確認できます。

1. 何を実現したいか

現在の範囲選択は 軸に平行な矩形のみです。 カメラで斜めから撮った書類、机の上のレシート、画面のスクショに写り込んだ ドキュメント (Zoomウィンドウ内の PDF 等) のように、ドキュメントが遠近で歪んでいるケースでは、 矩形選択だと余計な背景が入ったり、そもそも文字が斜めのまま PARSeq に流れて認識精度が落ちる問題があります。

参考リポジトリ ( ndlocr-lite-wasm ) では、ユーザーが 4 点 (角) をドラッグ して ドキュメント領域を指定 → その 4 点を「正面から見た矩形」に対応させるホモグラフィ変換 → 変換後の綺麗な矩形画像を OCR、というフローが取れています。 同じことをオフラインOCR拡張の viewer に載せます。

ユースケース

  • スマホで撮ったレシートを拡張の viewer に開いて、傾き補正して OCR
  • Zoom などで共有された画面キャプチャの中の文書領域だけを台形選択
  • 雑誌・書籍の見開きスキャンで、片方のページだけ抜き出す
  • スクリーンショット内で斜めに配置されたラベル・チップ

2. 既にあるもの / 足りないもの

✅ すでに実装済み

  • computeHomography(src[4], dst[4]) — 4対応点から 3×3 ホモグラフィを解く (Gaussian elimination, 8×9 行列)
  • applyPerspective(imageData, matrix, outW, outH) — 逆マッピング + バイリニア補間で変換画像を生成
  • Point { x, y } の型定義
  • 上記は src/ocr/engine/perspective.ts に 135 行、 単体テスト無しで置かれている

🚧 これから作るもの

  • viewer の 4 点ドラッグ UI (角ハンドル、edge line、外側ダーク overlay)
  • 「範囲選択 (矩形)」と切り替える モード切替 UI (toolbar に「台形選択」ボタン追加)
  • リアルタイム 変換プレビュー (小サイズ・軽量)
  • 確定 → applyPerspective → 既存の OCR パイプラインに 画像を流す配線
  • vitest ユニット (computeHomography/applyPerspective の再現性) + Playwright E2E (ドラッグ → プレビュー → OCR の end-to-end)

3. UX — どこにどう出すか

3-1. ツールバーへのボタン追加

viewer の toolbar に 「台形選択」 ボタンを1つ追加します。既存の「範囲選択」 と並列のモードで、どちらか片方だけがアクティブになる排他制御。

3-2. モード遷移

  • 「台形選択」クリック → 画像上に 初期の4点 (画像の 10% マージン内側に自動配置) が表示され、それぞれドラッグで移動可能に
  • 4点で囲まれた領域が 4角形 (quad) として青枠で描かれ、 外側は 40% 暗い overlay で覆う (どの領域を選んでいるか瞬時に分かるように)
  • 画面右下または画面下部に 小さなプレビュー (200px × auto) が表示され、 現在のquad を「正面から見た矩形」に変換した結果が リアルタイムで更新される
  • 「この領域でOCR」ボタンで確定 → 変換画像を OCR パイプラインに流し、 結果はクリップボード + OCR履歴 (これまで通り)
  • Esc でモードから抜ける (通常のビューに戻る、選択破棄)

4. アーキテクチャ / データフロー

既存の「範囲選択 → captureVisibleTab → 矩形クロップ → OCR」 フローの中に、「台形選択」経路を並列に追加します。

1. Viewer 画像 or PDF ページを表示
→
2. Quad UI (NEW) 4 点ドラッグで台形選択
→
3. Warp (NEW) applyPerspective で矩形化
→
4. OCR 既存 offscreen worker (DEIM + PARSeq)
→
5. Result Clipboard + OCR履歴
ポイント
既存の「範囲選択 (矩形)」経路は変更しない。「台形選択」は 新しい選択モード として並列に増やす。DEIM / PARSeq から見れば「1 枚の PNG を渡される」ことに変わりはないので、 変換後の画像を上流で作って渡すだけ。

5-2. quad-selection.ts の外形

// 純粋ロジック層 — 描画・イベントは呼び出し側で
export interface QuadState {
  corners: [Point, Point, Point, Point]; // TL, TR, BR, BL
  draggingIndex: -1 | 0 | 1 | 2 | 3;
}

// 初期化: 画像サイズから 10% inset した quad を返す
export function initQuad(w: number, h: number, marginRatio = 0.1): QuadState;

// ドラッグ中の座標更新。制約 (画像外に出ない・quad が反転しない) を適用
export function moveCorner(
  state: QuadState,
  idx: 0 | 1 | 2 | 3,
  p: Point,
  imgW: number,
  imgH: number,
): QuadState;

// クリック位置が既存の角ハンドル近傍 (GRAB_RADIUS 内) かを判定
export function hitTestCorner(
  state: QuadState,
  p: Point,
  handleRadiusPx: number,
): -1 | 0 | 1 | 2 | 3;

// quad の 4 辺の長さから「補正後の出力サイズ (rectangle)」を決める
export function suggestOutputSize(state: QuadState): { w: number; h: number };

// canvas に quad を描画 (外側 dim overlay + 4 lines + handles)
export function drawQuad(
  ctx: CanvasRenderingContext2D,
  state: QuadState,
  imgW: number,
  imgH: number,
  displayScale: number,
): void;

描画とロジックを分けることで、 vitest では moveCorner の制約や suggestOutputSize の計算だけを純粋にテストできます。Canvas 描画は Playwright E2E で覆う想定。

5-3. viewer.ts への差し込みポイント

// 既存のフラグに並列で追加
let selectMode = false;      // (既存) 矩形選択
let quadMode = false;         // (新規) 台形選択
let quadState: QuadState | null = null;

// toolbar
btnQuadSelect.addEventListener("click", () => {
  if (!img) return;
  selectMode = false;                         // 排他
  quadMode = true;
  quadState = initQuad(canvas.width, canvas.height);
  canvas.style.cursor = "crosshair";
  drawImage();
  drawQuad(ctx, quadState, canvas.width, canvas.height, /*scale*/ 1);
  updatePreview();
});

// 確定 (「この領域でOCR」)
async function confirmQuad(): Promise<void> {
  if (!quadState) return;
  const { w: outW, h: outH } = suggestOutputSize(quadState);
  const H = computeHomography(
    quadState.corners,
    [{x:0,y:0},{x:outW,y:0},{x:outW,y:outH},{x:0,y:outH}],
  );
  const srcData = ctx!.getImageData(0, 0, canvas.width, canvas.height);
  const warped = applyPerspective(srcData, H, outW, outH);
  // warped を PNG Blob 化して既存の runOcr の入り口に流す
  await sendToOcrPipeline(warped);
}

6. パフォーマンス設計

applyPerspective は逐次スキャン + バイリニア補間なので、フル解像度で毎フレーム 走らせるとドラッグがカクつきます。以下 2 段構え:

  • ドラッグ中: 画像を 1/4 程度に縮小した lowResSrc に対して applyPerspective を走らせ、 プレビューは 200px 幅程度の小さな canvas に描画。 (参考リポジトリと同じ方針)
  • 確定時 (OCR 実行時): フル解像度の imageData に対して 1 回だけ applyPerspective を走らせる。 OCR の DEIM 推論 (数百 ms 〜) に比べれば十分小さいコストで済む。
計測タスク
1080×1920 のスマホ写真クロップに対する フル解像度 applyPerspective の実行時間を Chromium で測定する (目安: 500ms 以内であればユーザー体験としては十分)。 必要ならピクセルループを OffscreenCanvas + drawImage ベースの近似実装に差し替え可能 (品質は落ちるが数十msで済む)。

7. UX 決定事項 / Open Questions

# 論点 現時点の案
Q1 初期の 4 点の配置 画像の 10% inset に自動配置 (ndlocr-lite-wasm と同じ)
Q2 quad が凹型 (self-intersecting) になったら? moveCorner の時点で凸性チェック、凹になる操作は隣接する軸の位置に クランプ (制約付き移動)
Q3 プレビューの縦横比 quad の 4 辺の長さから最大の高さ・幅を採用し、 近い実寸で補正 (ndlocr-lite-wasm 準拠)
Q4 タッチデバイス対応 Pointer Events で mouse/touch を統合。ハンドル判定は GRAB_RADIUS を可変にして touch では大きめ (24px)
Q5 右クリック context menu (画像を右クリック→開く) から入れる? Phase 1 では viewer 内のボタンのみ。Phase 2 で context menu 経由も検討
Q6 PDF ページ上でも動く? viewer が PDF ページを 1 枚の canvas として持つので、 画像モードと同じロジックがそのまま動く (追加実装不要)
Q7 OCR 履歴のラベル 画像モード: 従来通り。PDF モード: filename.pdf#p3 (quad) のように quad 使用を明示

8. テスト戦略

vitest (Node)

  • computeHomography: 恒等 (src==dst) が単位行列を返す / 軸並行の矩形→矩形が平行移動+スケール行列を返す / 退化ケース (3 点共線) が例外を投げる
  • applyPerspective: 単位行列で画像がそのまま出る / 90度回転行列で画像が回る / グラデーション画像で補間結果が滑らか
  • quad-selection.ts: moveCorner が凸性維持 / suggestOutputSize の縦横比

Playwright E2E

  • viewer.html で fixture 画像を開き、 「台形選択」→ 4 点ドラッグ → 「この領域でOCR」→ 認識テキストが期待文字列を含む
  • PDF モードで台形選択が動くこと
  • Esc でモードを抜けられること

10. リスクと対応

リスク対応
フル解像度の applyPerspective が遅い (>1s) 計測タスクを先に走らせ、遅ければ OffscreenCanvas + drawImage の近似実装に差し替え
凹型 quad で PARSeq が混乱する moveCorner の時点で凹型を作れない制約を入れる (自動クランプ)

## はじめに

[Chrome拡張「オフラインOCR」](https://chromewebstore.google.com/detail/offline-ocr/cfppiicaeemimcbodibggnnolckcpmpd) の、GitHub Pages の紹介サイトと紹介動画を作り直しました。

https://tamoco-mocomoco.github.io/offline-ocr/

前のサイトと動画は、[2 本目の記事](https://zenn.dev/lecto/articles/3b1606a8ac859e) で書いたとおり、Claude（Claude Code）に HTML + CSS で作ってもらったものです。中身は正確なのですが、見た目が「資料」っぽく、少し固い。そこで今回は、**手元で動く画像生成サーバー（imagegen）でイラストを足して、ポップにしてみました**。

ただ、オフラインOCR の一番の売りは「通信ゼロで安全」なことです。ポップにしすぎると軽く見えてしまうので、**落ち着いた土台に、イラストで明るさを足す** くらいのバランスにしています。その途中で、画像生成ならではの落とし穴（**それっぽいけど読めない文字**）にもはまったので、あわせて書きます。

## Before: 何が固かったのか

前のサイトは、実はストアのスクリーンショット用の HTML（`store/screenshots.html`）を、そのまま GitHub Pages の index にしたものでした。1280×800 のスライドが縦に並んでいるだけなので、

- **見た目が「資料」**: 青いグラデーションと、絵文字のアイコンと、文字のカード。正確だけど、わくわくはしない
- **機能が古い**: 載っているのは v0.2 ごろまでの機能。画像ビューア、PDF、OCR の履歴、ゆがみ補正、消しゴムといった、あとから増えた機能が入っていない
- **動画が長い**: 紹介動画は 6 場面で 3 分 28 秒。機能説明としては丁寧だけど、ティザーとしては長い

ストアのスクリーンショットとしては今でも使うので、`store/screenshots.html` はそのまま残し、紹介サイトは `site/` に別に作ることにしました。

## やってみた 1: アニメ向けのモデルで描くと、文字が「それっぽいだけ」になる

最初は、たもこの絵でも使っている `anime`（Animagine XL 4.0）で、使い道のカードに載せる「漫画」の絵を描いてみました。Danbooru 形式のタグで指示します。

```text
no humans, still life, open manga book, comic panels, speech bubbles, vertical text,
pastel colors, soft lighting, flat color, simple background, light blue background, cute illustration
```

![アニメ向けのモデルで描いた漫画の絵。吹き出しの中の文字は、ひらがなに見えるが意味がない](/images/11-02-anime-fake-text.png)

パステルでかわいいのですが、**吹き出しの中を見てください**。ひらがなっぽい形が並んでいるのに、読めません。

せっかくなので、この吹き出しを **オフラインOCR そのもの** に読ませてみました。

| 切り抜いた所 | OCR の結果 |
| --- | --- |
| 右の大きな吹き出し | `かないか` |
| 左の小さな吹き出し | `2` |

意味のない文字です。OCR の紹介サイトに「読めない文字」の絵が載っていて、試しに OCR したらこうなる……のは、さすがに困ります。

## やってみた 2: 日本語が得意なモデルに替えて、OCR で検品する

次に、日本語・漢字の文字入りの絵が得意な `zimage-turbo`（Z-Image-Turbo）に替えました。こちらは自然文で指示します。描かせたい文字は、ダブルクォートで囲んでそのまま書きます。

```text
A cute Japanese manga panel. A cheerful girl with long pink hair raises her fist happily.
Next to her is a large round white speech bubble with bold black vertical Japanese text
that reads "今日もがんばろう！".
Soft flat vector illustration, pastel blue, mint and cream colors, ...
```

![Z-Image-Turbo で描いた吹き出し。読める字になったが……](/images/11-03-ganbaru.png)

**ちゃんと読める字になりました。** 縦書きで、右の列から「今日も」「がんばろう」。……と思ったのですが、念のため OCR に読ませると、

```text
今日も
がんばるう
```

よく見ると、**絵のほうが「ろ」を「る」と書きまちがえていました**。OCR は正しく読んでいて、まちがっていたのは絵です。人の目だと「がんばろう」と思い込んで見落としていました。

ほかの絵も、OCR に通してみると、こうなりました。

| 絵 | 描かせた文字 | OCR の結果 | 絵を見ると |
| --- | --- | --- | --- |
| 漫画 | また明日ね | `また明日ね` | ◯ |
| 新聞 | 朝のコラム | （絵全体では何も読めず）／見出しを囲むと `朝のコラム` | ◯ |
| 本 | 第一章 | `第一章` | ◯ |
| PDF | 報告書 | `報告書`（ほかに画面の飾りの崩れた字も） | ✗ 拡大すると「報」も「書」も崩れている（あとで気づきました。後述） |
| 日本酒 | 純米吟醸 | `純来哈醇` | ✗「純**来**吟醸」と書かれている |
| 請求書 | 請求書 | `舗求名` | ✗ 中国の簡体字のような「辅求书」 |

![誤字のあった絵。左から「おばよう！」「純来吟醸」、「請」が書けていない請求書](/images/11-04-typos.png)

漢字は形がそれっぽいぶん、**ぱっと見では誤字に気づきにくい** です。新聞は、絵全体だと読めませんでしたが、見出しを囲んで読ませると `朝のコラム` と正しく出ました。拡張はふだん範囲を選んで使うものなので、これは実際の使い方どおりです。

### 検品をテストにする

そこで、**描いた絵を OCR に通して、描かせた文字と合うかを確かめる** ことにしました。オフラインOCR には、Playwright で OCR のパイプラインを動かす E2E テストの仕組み（`test/e2e/harness`）があります。それを使って、手元の画像を読む spec を足しました。

```ts:test/e2e/ocr-images.spec.ts
test("OCR local images", async ({ context }) => {
  const specs = (process.env.OCR_IMAGES ?? "").split(";").filter(Boolean);
  test.skip(specs.length === 0, "OCR_IMAGES is not set");
  const page = await context.newPage();
  await page.goto("/test/e2e/harness/index.html");
  await page.waitForFunction(() => window.__ocr !== undefined);
  await page.evaluate(() => window.__ocr.whenReady());
  for (const spec of specs) {
    const [file, box] = spec.split(":");           // a.png:x,y,w,h なら切り抜いてから
    let bytes = readFileSync(file);
    // ...(切り抜きは省略)
    const r = await page.evaluate(async (b) => await window.__ocr.run(b), Array.from(bytes));
    console.log(`OCR ${file} => ${JSON.stringify(r.text)}`);
  }
});
```

```bash
OCR_IMAGES="hero.png;use-sake.png" npm run test:e2e -- ocr-images
```

拡張そのものと同じモデル・同じ前処理で読むので、「サイトに載せた絵を、見た人が拡張で OCR したらどうなるか」をそのまま確かめられます。

あとは、絵の指示（`site/assets-src/prompts.json`）に「本当はこう読めるはず」という `expect` を足して、**描く → OCR で読む → くらべる** を、合うまで seed を替えてくり返すだけです。

ループは小さな Python で、画像生成サーバーの HTTP API（`POST /generate`）で描き、上の spec で読ませて、`expect` が含まれているかを見ます。1 枚あたり、描くのに 90〜100 秒、OCR は数秒でした。結果はこうなりました。

| 絵 | 試した seed | OCR の結果 | どうしたか |
| --- | --- | --- | --- |
| 吹き出し「今日もがんばろう！」 | 11、111 | どちらも「がんばるう」 | セリフを替えた |
| 吹き出し「おはよう！」 | 111〜411 の 4 回 | `おばよう!` が 3 回、`おばよ!` が 1 回 | **文字なしで描かせた** |
| 日本酒「純米吟醸」 | 13〜513 の 6 回 | 6 回とも「純来」 | 「大吟醸」に替えた |
| 日本酒「大吟醸」 | 113 | `大吟醸` | 合格にした（**でも、まちがいだった**。後述） |
| 請求書「請求書」 | 15〜515 の 6 回 | `鯨兼書`、`縣求名` など、6 回とも「請」が書けない | **文字なしで描かせた** |

seed を替えても、同じ字を同じようにまちがえます。「純米」は 6 回とも「純来」、「おはよう」は 4 回とも「おばよう」でした。**このモデルが苦手な字は、何回くり返しても直らない** ようです。

なお、請求書の seed 115 と 215 は、ループをやり直したときにもう一度描いていますが、2 回とも同じ絵になり、OCR の結果も 1 文字まで同じでした。seed を固定すれば同じ絵になるので、検品の記録として残せます。

### 直らない文字は、絵に描かせない

最後に落ち着いたのは、**文字は絵に描かせず、HTML で重ねる** というやり方です。吹き出しは「中に何も書かれていない」絵として描かせて（`expect` を空にして、OCR で文字が出ないことを確かめます）、セリフは CSS の縦書き（`writing-mode: vertical-rl`）で上に重ねました。

![左が文字なしで描かせた吹き出し、右がサイトで文字を重ねたところ](/images/11-05-empty-bubble.png)

```css
/* 吹き出しの文字は絵に描かせず、ここで重ねる */
.browser .view { container-type: inline-size; }
.say {
  position: absolute; transform: translate(-50%, -50%);
  writing-mode: vertical-rl;
  font: 900 8cqw/1.3 'Zen Maru Gothic', sans-serif;   /* 絵の幅に合わせて大きさが変わる */
}
```

ページの上の本物の文字なので、誤字は起きません。拡張で囲めば OCR でもそのまま読めます。サイトを撮って、選択枠と同じ範囲を spec に通すと、

```text
今日も
がんばろう!
```

と出ました。請求書の絵も、文字のない書類とはんこにして、「請求書」という言葉はカードの見出し（HTML）で出しています。

### OCR で合格でも、目で見ると誤字だった

これで全部そろった……と思って、公開前にカードの絵を拡大して見直したら、**OCR で合格にした絵にも誤字がありました**。

![OCR は「大吟醸」と読んだが、絵の「醸」は中国の簡体字だった](/images/11-09-jo-simplified.png)

日本酒のラベルの「大吟醸」は、「醸」が中国の簡体字（酿）で描かれていました。seed を替えて 4 回描き直しても、5 回とも同じ簡体字です。ところが OCR は、5 回とも `大吟醸` と読みました。PDF の「報告書」も同じで、描き直すと「書」が簡体字（书）になりましたが、そのうち 1 回は OCR が `報告書` と読んでいます。

理由は、OCR が出せる文字の一覧にありました。オフラインOCR のモデル（NDLOCR の PARSeq）が出せるのは、日本の資料のための 7,141 字だけです（`src/ocr/config/charset.ts`）。この一覧に「酿」や「书」はないので、OCR は **いちばん近い日本の字に読み替えます**。日本の資料を読む OCR としては正しい動きですが、絵の検品には向きません。

- **OCR で ✗ なら、絵はまちがっている**（「がんばるう」「純来」）
- **OCR で ◯ でも、絵が正しいとは限らない**（「酿」→ `醸`、「书」→ `書`）

そこで、OCR に通したあと、**文字を拡大して目でも確かめる** ことにしました。そのうえで、こう直しています。

| 絵 | 試したこと | どうしたか |
| --- | --- | --- |
| 日本酒「大吟醸」 | seed 113、31〜34 の 5 回とも「酿」 | 中国の簡体字と形が同じ字だけでできた「**辛口**」に替えた（1 回目で `辛口`、目で見ても正しい） |
| PDF「報告書」 | seed 17、31〜34 で「書」が「书」 | 「企画案」に替えたが、2 回とも「画」の中の「田」の下の線が欠けた |
| PDF「企画案」 | 文字なしで描かせると、画面がほぼ白で寂しい | 描いた題名を紙の色で消して、**ヒラギノ角ゴで組み直した**（PDF の題名はもともと活字なので） |

最後の「組み直す」は、変換スクリプト（`site/assets-src/make_assets.py`）でやっています。`prompts.json` に消す範囲と文字を書いておくと、webp にする前に重ねます。

```json:site/assets-src/prompts.json（抜粋）
"retype": { "text": "企画案", "box": [300, 340, 850, 545], "fill": [255, 255, 255], "color": [17, 17, 17], "size": 160 }
```

ついでに、本のカードも描き直しました。スマホで本を撮る絵にしていたのですが、見直すと **スマホの上に紙が載っている** ように見えました。ゆがみ補正は「四隅を合わせて平らにする」機能なので、斜めに置いた本の四隅に印を付けた絵にしています。この絵は、斜めのままだと OCR が何も読めませんでした。まさに、ゆがみ補正が要る絵です。

最終的に使った絵は、こちらの 6 枚（と、吹き出し・安全の絵の 2 枚）です。描いた枚数は、試しも入れて全部で 44 枚でした。

![最終的に使ったカードの絵](/images/11-06-cards.png)

## ポップと安全のバランス

絵がそろったところで、最初は **太い黒い線と、大きくずらした影** の、かなりポップなデザインにしました。ステッカーのような見た目で、たしかに明るくはなります。

ただ、オフラインOCR を選んでくれる人の多くは、「画像を外に送りたくない」から使っています。ポップすぎると、**安全を売りにしている道具にしては軽く見える**。そこで、

- 土台は、前のサイトと同じ **紺と青**。線は細く、影はやわらかく
- 明るさは、**イラストと、少しの差し色**（ミント・コーラル・黄）だけで足す
- 見出しは角ゴシック、ラベルだけ丸ゴシック

という形にしました。あわせて、**安全の節をページの上のほう**（ヒーローのすぐ下）に移し、拡張が求める権限と、その理由を表にしています。

![安全の節。求める権限と、その理由を表にした](/images/11-07-safety.png)

この表を作るときにコードを読み直したら、**設定とクリーニングルールは `chrome.storage.sync` に保存している** ことに気づきました。Chrome の同期をオンにしている人は、自分の Google アカウントを通して同期されます（OCR の履歴は `chrome.storage.local` で、パソコンの中だけです）。「どこにも送らない」と言い切るより、こう書いたほうが正確なので、サイトにはそのまま書きました。

機能の一覧も、v0.9.1 までのものに更新しました。PDF、ゆがみ補正、消しゴム、OCR の履歴、4 行同時の読み取りなどです。最近の 5 回ぶんの更新も、時系列で載せています。

## 紹介動画も、3 分半から 40 秒のティザーに

紹介動画も、同じ絵を使って作り直しました。前は 6 場面で 3 分 28 秒の機能説明でしたが、今回は **7 場面・37.7 秒のティザー** です。

![作り直した紹介動画のコマ](/images/11-08-teaser.png)

作り方は前と同じで、HTML の場面を Playwright で録画し、ffmpeg で声と BGM を重ねます。今回は、台本を JSON にして、**声の長さから場面の時間を決める** ようにしました。

```json:store/video-v2/script.json（抜粋）
{ "id": "demo", "text": "オフラインOCRなら、囲むだけ。", "say": "オフラインオーシーアールなら、かこむだけ。", "hold": 1.6 }
```

1. `say`（読み）を VOICEVOX で声にして、WAV の長さを測る
2. 声の長さ＋`hold`（見せる間）＋すき間から、場面ごとの開始・終了の時刻を決める
3. ページの `start({ scenes })` を呼んで、その時刻どおりに場面を切り替えながら録画する
4. 声を `adelay` で時刻に置き、BGM を下に敷いて MP4 にする

読みは、字幕とは別に `say` でひらがな・カタカナにしています（「OCR」は「オーシーアール」）。BGM は local-musicgen で「明るく、でも信頼感のある製品紹介」の曲を作りました（約 58 秒の曲で、生成は 17 秒でした）。

ひとつはまったのが音で、VOICEVOX の声（24kHz・モノラル）をそのまま最初の入力にすると、ffmpeg の `amix` の出力もそれに合わせられて、BGM までモノラルになっていました。`aformat=sample_rates=48000:channel_layouts=stereo` で、声も BGM もそろえてから重ねています。

## モデルのライセンスも確かめる

サイトや紹介動画は、拡張の宣伝に使うものです。なので、使ったモデルのライセンスも確かめました（2026/11/2 時点の Hugging Face のページ）。

| モデル | ライセンス | 今回の使い方 |
| --- | --- | --- |
| Z-Image-Turbo | Apache-2.0 | サイトと紹介動画の絵（仕上げ） |
| Animagine XL 4.0 | CreativeML Open RAIL++-M | 最初の試し（たもこの絵もこのモデル） |
| SDXL Turbo | Stability AI Community License | 今回は使っていない |

SDXL Turbo は、画像生成サーバーで「高速な下書き用」にしているモデルですが、ライセンス上、**商用で無料なのは年商 100 万ドル未満の場合だけ** です。宣伝に使う絵は、ライセンスのゆるいモデルで作るほうが安心です。

フッターには「イラスト：Animagine XL 4.0 で手元で生成」と書いていましたが、仕上げの絵はぜんぶ Z-Image-Turbo なので、ここも直しました。

## まとめ

- 手元の画像生成で、資料っぽかった紹介サイトに、イラストで明るさを足せた。外のサービスには何も送っていない
- ただし、**絵の中の文字は誤字だらけ**。それっぽい字ほど、人の目では気づきにくい
- 拡張そのものの OCR で検品する、という形にすると、「見た人が OCR したらどうなるか」まで確かめられる
- ただし、OCR は知らない字（中国の簡体字など）を近い日本の字に読み替える。**OCR で合格でも、最後は拡大して目で見る**
- 苦手な字は、seed を替えても直らない。**直らない文字は絵に描かせず、HTML や書体で重ねる** のがいちばん確実だった
- 安全が売りの道具なら、ポップさは「ほどほど」に。権限や保存先は、コードを読んで正確に書く

画像生成は「それっぽいもの」を一瞬で出してくれますが、それが本当に正しいかは別の話です。今回は、作った OCR が、作った絵の検品係になってくれました。
